# Устройство Go-бэкенда

Бэкенд использует стандартный `net/http` и `pgx`, без веб-фреймворка. Внешний контракт описан в [openapi.json](openapi.json). После рефакторинга пути, форматы JSON, роли, cookie и схема PostgreSQL сохранены; React не требует изменений.

## Где находится код

Пути в таблице отсчитываются от `backend/`.

| Файл или группа | Ответственность |
|---|---|
| `cmd/api/main.go` | Выбор CLI-команды и подключение к базе |
| `cmd/api/config.go` | Чтение и проверка параметров сервера до подключения к БД |
| `cmd/api/serve.go` | HTTP-сервер, завершение по сигналу, ежечасная очистка сессий |
| `internal/forum/server.go` | Настройки, конструктор и регистрация маршрутов |
| `http.go`, `middleware.go`, `frontend.go` | JSON и ошибки, request ID, защитные заголовки, Origin, раздача React |
| `auth.go`, `sessions.go`, `staff_sessions.go`, `security.go` | Идентификация, права/CSRF, независимые сессии посетителя и команды, криптография и сетевые лимиты |
| `catalog.go` | Чтение разделов, тем и постов; поиск и пагинация |
| `publishing.go` | HTTP-обработчики тем, ответов, удаления и жалоб |
| `publishing_service.go` | Валидация публикации, блокировки, транзакционные операции записи |
| `idempotency.go`, `rate_limit.go` | Общая транзакция публикации, сохранённые ответы, лимиты анонимной сессии |
| `moderation.go`, `admin.go` | HTTP-обработчики и валидация модерации/администрирования |
| `moderation_store.go`, `admin_store.go` | SQL, атомарные решения жалоб, журнал и смена ролей |
| `store.go`, `migrate.go`, `seed.go`, `staff_store.go`, `cleanup.go` | Пул PostgreSQL, миграции, демонстрационные данные, создание персонала, очистка |

Все файлы после `internal/forum/server.go` находятся в том же пакете `internal/forum`. Транзакционные методы получают `context.Context` и типизированные аргументы; они не принимают `http.Request` или `ResponseWriter`. Небольшой проект остаётся одним пакетом: отдельные repository-интерфейсы и контейнер внедрения зависимостей не требуются.

## Границы транзакций

- Каждая анонимная запись блокирует действующую сессию. Конкурирующие публикации одной сессии не обходят ограничение частоты.
- `publishOnce` проверяет сохранённый ответ после блокировки сессии, но до проверки изменяемого состояния темы и новых лимитов. Тема/пост, событие лимита и ответ для повтора фиксируются одной транзакцией.
- Хеш идемпотентности сохраняет прежнее представление: путь плюс нормализованный JSON с исходным порядком полей. Уже сохранённые ключи совместимы с новой версией.
- Решение жалобы блокирует её строку; видимость поста, результат жалобы и запись журнала фиксируются вместе. Ошибка журнала откатывает решение.
- Смена роли использует общую advisory-блокировку. Проверка последнего администратора, изменение роли и отзыв его служебных сессий атомарны.
- При завершении сервера фоновая очистка отменяется и завершается до закрытия пула БД.

## Изменения в проверке ошибочного ввода

`Content-Type` разбирается как MIME-тип: `application/json; charset=utf-8` допускается, а `application/jsonp` и `application/json-invalid` дают 415. `APP_ORIGIN` должен быть точным origin без пользовательских данных, пути, query и fragment. Пустой порт, явно указанный порт по умолчанию (`:80` для HTTP, `:443` для HTTPS) и порт вне диапазона 1–65535 отклоняются. Браузер опускает порт по умолчанию в заголовке Origin, поэтому его нужно опускать и в настройке. Ошибочная конфигурация выявляется до подключения к PostgreSQL.

## Проверки

```sh
make test
make integration
make e2e
```

Модульные тесты дополнительно покрывают конфигурацию запуска, HTTP-декодирование и ошибки, Origin/CSRF/права, статические файлы, совместимость сохранённых публикаций и валидацию модерации. Интеграция проверяет реальные транзакции PostgreSQL и запускается с `-race`; E2E проверяет неизменённый React через HTTP.

Фактические результаты и ограничения приёмки — в [TESTING.md](TESTING.md). Сгенерированный справочник внутренних объявлений — в [generated/go-code.txt](generated/go-code.txt).
